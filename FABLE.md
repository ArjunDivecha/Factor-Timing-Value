## 1. Assessment (honest, evidence-backed)

**The trading engine is the strongest part of the repo and should be treated as load-bearing,
not re-litigated.** `Step Schwab Trading.py` has been through an adversarial multi-model review
and carries 33 fixture-based safety tests (`tests/test_schwab_twap_engine.py`, all green today),
with fails-closed patterns (market-order cleanup aborts on quote failure, atomic live-marker
via `O_EXCL`, broker-confirmed carry-forward). It must stay byte-for-byte identical to the sibling
Momentum repo modulo account constants — that invariant is real and correctly documented.

**The research pipeline is the soft underbelly.** It is a mature, sequential Excel-passing
pipeline (21 steps) that is well-commented but has **zero automated tests** — the only test file
covers trading. The single most consequential correctness surface, the Bloomberg data-quality
guard `detect_regime_breaks_sheet` (`Step One Create T2Master.py:196-334`, wired in at
`:826-977`), is untested despite feeding alphas that drive *real-money* rebalances. Its two
load-bearing behaviors — forward-only correction (a hard project invariant) and actually catching
the documented bimodal near-zero Bloomberg failures — are unprotected against silent regression.

**Documentation drift is systemic and, for a live-money system, a genuine hazard, not cosmetic.**
Concrete instances found: `Step Five FAST.py` is the active engine but its own header reads
`SCRIPT NAME: Step Five Top3 Tcost.py` (`Step Five FAST.py:3`); the pre-existing CLAUDE.md command
list pointed at scripts that do not exist (`Step Five 60 Month Optimal Portfolios.py`,
`Step Three Top20 Portfolios.py`); and both CLAUDE.md and AGENTS.md described the regime-break
detector as "proposed but not yet implemented" when it is fully wired in and writing
`T2_regime_break_log.xlsx`. An operator trusting stale docs could run the wrong step against a
real account. (This review's CLAUDE.md rewrite corrects these.)

**Smaller real issues.** (a) `Run_Limited_Pipeline.py:2` — module docstring still says
"Run_All_Pipeline.py" (copy-paste); the two runners are otherwise distinct and correct. (b)
`requirements.txt:1-19` pins everything with `>=`, so a fresh environment can pull a newer
pandas/numpy and silently shift numeric backtest outputs — a reproducibility risk for a system
that trades on those numbers. (c) The guard's Pass-C audit label at
`Step One Create T2Master.py:324` computes `'cross-sectional' if i in is_bad.index[is_bad[col]]`
against the *final* `is_bad` (post Pass B), so a Pass-B-flagged cell can be mislabeled
"cross-sectional" in the log — logging-only, but it corrupts the audit trail.

Net: the code is fundamentally sound and the risky part (trading) is well-defended. The gap is
**verification of the research/data-quality layer**, and secondarily **doc/repro hygiene**.

## 2. Prioritized improvements

### P0 — Lock the data-quality guard with deterministic tests
- **What & why:** `detect_regime_breaks_sheet` (`Step One:196`) is the root defense against the
  documented bimodal Bloomberg corruption that poisons alphas → poisons real trades. It has no
  tests. The repo already demonstrates the exact discipline needed (the Schwab pytest harness).
- **Falsifiable bet:** *if* the guard is run on a fixture reproducing a sustained near-zero streak
  below the cross-sectional floor with distinct good values before/after, *then* every flagged
  cell is forward-filled from a strictly earlier row (never later; NaN if none) and the whole
  streak is neutralized, *observable* via `python3 -m pytest tests/test_data_quality_guard.py`
  exiting 0.
- **Invariants:** forward-only correction (no backfill/lookahead); bimodal regime fully
  neutralized; clean data returned unchanged; behavior pinned by a golden-master; diff confined
  to test files.
- **Gate intent:** new `tests/test_data_quality_guard.py` passes; a back-fill mutation of the
  guard turns the forward-only case red; `git diff --name-only` ⊆ scope.
- **Effort:** ~2-4 hours. **(Full contract below.)**

### P1 — Golden-master / characterization harness for numeric pipeline outputs
- **What & why:** With no tests, any refactor of Step Five/Six/Eight can silently change the
  weights that get traded. A snapshot test comparing a rerun's key outputs
  (`T2_rolling_window_weights.xlsx`, `T2_Final_Country_Weights.xlsx`) against committed reference
  frames within a numeric tolerance makes refactors safe.
- **Falsifiable bet:** *if* the pipeline is rerun on the committed `T2 Master.xlsx`, *then* the
  regenerated weights match the reference snapshot within tolerance (e.g. 1e-6), *observable* via
  a pytest that loads both and asserts `np.allclose`.
- **Invariants:** deterministic given fixed input; tolerance is explicit; snapshot is versioned.
- **Gate intent:** `pytest tests/test_pipeline_snapshot.py` exits 0; a deliberate 1% weight
  perturbation turns it red.
- **Effort:** ~half a day (needs one clean reference run to capture snapshots).

### P1 — Pin dependency versions for numeric reproducibility
- **What & why:** `requirements.txt:1-19` uses `>=`. A future `pip install` can pull a pandas/numpy
  that changes rounding/aggregation and thus the traded weights, with no signal.
- **Falsifiable bet:** *if* deps are pinned (`==` or a lockfile) and reinstalled, *then* the
  snapshot test above still passes bit-for-bit, *observable* via clean-venv install + snapshot.
- **Invariants:** the pinned set installs cleanly on Python 3.14; no transitive drift.
- **Gate intent:** `pip install -r requirements.txt` in a fresh venv succeeds AND the snapshot
  test passes.
- **Effort:** ~1 hour (pair with P1 snapshot).

### P2 — Fix the Pass-C detection label in the regime-break log
- **What & why:** `Step One:324` mislabels Pass-B (time-series) flags as "cross-sectional" in
  `T2_regime_break_log.xlsx` because it re-reads the final `is_bad`. Audit-trail correctness only.
- **Falsifiable bet:** *if* Pass A and Pass B are tracked separately, *then* each replacement's
  `detection` field matches the pass that flagged it, *observable* via a unit test on a fixture
  with one xs-flag and one ts-flag asserting the two labels.
- **Invariants:** label ∈ {cross-sectional, time-series}; fill values unchanged (behavior-preserving).
- **Gate intent:** a targeted pytest case asserts correct labels; the golden-master (P0 INV4) still passes.
- **Effort:** ~30 min. *Do after P0* so the golden-master guards the behavior first.

### P2 — Fix `Run_Limited_Pipeline.py` docstring
- **What & why:** `Run_Limited_Pipeline.py:2` claims it is `Run_All_Pipeline.py`; misleads operators.
- **Falsifiable bet:** *if* the docstring names the correct file and its partial scope, *then* a
  grep for the wrong name returns nothing, *observable* via `grep -c "Run_All_Pipeline" Run_Limited_Pipeline.py` == 0.
- **Gate intent:** grep returns 0. **Effort:** ~5 min.

## Context

Repo root: `/Users/arjundivecha/Dropbox/AAA Backup/A Complete/T2 Factor Timing Fuzzy Value`.
This is the Value/Quality country-allocation pipeline whose factor alphas drive a **live
real-money Schwab rebalance** (account #167). Bad input data therefore flows straight into
real trades. `Step One Create T2Master.py` cleans raw Bloomberg data and contains the
data-quality guard `detect_regime_breaks_sheet(data, sheet_name, xs_threshold=0.05,
ts_pct_threshold=0.80, ts_median_window=12)` (defined near line 196, invoked in the sheet loop
around lines 826-977, logging to `T2_regime_break_log.xlsx`). The guard runs two passes —
Pass A flags a cell below `xs_threshold * cross_sectional_median` (the documented bimodal
Bloomberg failure where one country's valuation collapses to ~0.03 while peers sit at 5-20),
Pass B flags time-series spikes deviating > `ts_pct_threshold` from both preceding and following
medians — then Pass C forward-fills flagged cells with the last preceding good value.

Two behaviors are load-bearing and currently have **zero automated tests** (only the Schwab
trading engine is covered, by `tests/test_schwab_twap_engine.py`): (1) correction must be
**forward-only** — a hard project invariant that no future data may propagate backward — and
(2) the guard must actually catch the sustained near-zero regimes that motivated it, without
corrupting good data. Tests run from the repo root with `python3 -m pytest tests/ -q` (33 pass
today). The task is to add `tests/test_data_quality_guard.py` locking these invariants against
synthetic fixtures. Build Mode must find an import path to the function that does not execute
the full pipeline; if Step One is not import-safe, the only permitted edit to it is minimal
import-safety scaffolding (e.g. a `if __name__ == "__main__"` guard) that leaves the guard's
logic bit-for-bit unchanged. No real `.xlsx`/`.csv` data files may be created or modified.

## Build Loop vs Product Loop

The **build loop** is fully machine-checkable: the four gates prove, via pytest on synthetic
fixtures plus a git-diff scope check, that the guard forward-fills only from earlier rows
(INV1), neutralizes the documented bimodal near-zero regime (INV2), leaves clean data untouched
(INV3), reproduces a committed golden-master output so future logic edits are caught (INV4),
and that nothing outside `scope.in` changed (INV5). Passing these gates proves the guard's
behavior is pinned and lookahead-free on the tested fixtures.

The **product loop** is the real-world bet that cleaner, invariant-protected input data yields
correct country alphas and therefore better real-money rebalances on account #167. That
outcome can only be judged after a live monthly run against fresh Bloomberg data and observed
fills — it is not provable from fixtures. The coding model **may not claim** the product bet
(improved real-money outcomes, or that all Bloomberg corruption is caught) is satisfied merely
because the build-loop gates pass; gate success proves the implementation contract, not the
product bet.
